# 项目开发维护索引怎么建

这份说明是给 base 和各具体项目复用的通用规则。

它要解决的问题不是“再多写一份大文档”，而是给长期维护项目补一层**轻量索引层**，让后续 AI 和新人维护者接手时，能先知道：

- 正式文档入口在哪里
- 通用规则先看哪里
- 项目私有坑先看哪里
- 当前重点模块入口在哪里
- 常见开发动作先从哪层文档进
- 哪些经验要回灌 base，哪些只留项目内

## 1. 什么情况下项目应该建立“开发维护索引”

满足下面任一条，就建议建立：

1. 项目已经进入长期维护阶段，不再是刚初始化的空项目
2. 项目文档已经超过“新人一眼看完”的规模，接手时容易找不到入口
3. 项目已经出现模块 README、系统文档、坑位文档、任务执行卡并存的情况
4. 项目已经和 `base` 产生了一些实际差异，不能再只靠模板理解
5. 后续维护者可能不是当前开发者本人，而是新的 AI 或新人同学
6. 项目已经开始出现“这个问题先看哪里”说不清的情况

反过来，如果还是很小的短期项目、几乎没有正式文档、也没有长期维护预期，就不用急着补这份索引。

## 2. 这份索引至少应包含哪些内容

一份合格的 `docs/00-system/项目开发维护索引.md`，至少回答下面 6 类问题：

1. **正式文档入口有哪些**
   - `docs/README.md`
   - `docs/00-system/`
   - `docs/01-modules/模块名/README.md`
   - 版本文档
   - 任务执行卡
2. **通用规则看哪里**
   - `AGENTS.md`
   - 端内 `AGENTS.md`
   - 通用开发规范
   - `cool-project-stack` / `cool-team-docs`
3. **项目私有坑 / 兼容记录看哪里**
   - 项目专属坑位文档
   - 项目与 base 差异文档
4. **当前重点模块入口有哪些**
   - 当前应重点维护的模块 README
   - 相关代码目录落点
5. **常见开发动作先看哪里**
   - 新功能
   - 改接口
   - 改数据库
   - 排查项目特有 bug
6. **哪些经验应回灌 base，哪些只留项目内**
   - 通用规则上提
   - 项目私有坑留本地

写法要求：

- 用中文
- 轻量、务实
- 以入口和判断为主，不堆大段背景知识
- 让后续维护者能快速决定“下一步先看哪里”

## 3. 它和其他文档是什么关系

## 3.1 和 `docs/README.md` 的关系

- `docs/README.md` 是项目文档总入口
- 它负责文档索引、问题索引、维护入口索引
- `项目开发维护索引.md` 是 `docs/README.md` 下的一层专项维护索引，重点解决“长期维护时怎么快速定位入口”

简单理解：

- `docs/README.md` 管全局导航
- `项目开发维护索引.md` 管长期维护接手导航

## 3.2 和模块 README 的关系

- 模块 README 管某一个模块的正式入口
- 它要回答模块背景、阅读顺序、当前版本、长期约束、常见修改入口、代码落点
- 项目开发维护索引只负责把人导向对应模块 README，不替模块 README 写细节

## 3.3 和项目专属坑位文档的关系

- 项目专属坑位文档记录项目私有坑、历史兼容点、项目偏差
- 项目开发维护索引只负责告诉维护者：什么时候应该先去看坑位文档
- 不要把项目坑全文复制到索引里

## 3.4 和任务执行卡的关系

- 任务执行卡记录当前阶段、待确认点、下一步动作
- 它是任务级、迭代级文档，不是项目长期总入口
- 项目开发维护索引只负责告诉维护者：当前任务推进状态要去哪里看

## 4. 建立索引时的最小落地动作

如果判断一个项目应该建立开发维护索引，最少要同步做这几件事：

1. 新增 `docs/00-system/项目开发维护索引.md`
2. 更新 `docs/README.md`，给这份索引留正式入口
3. 检查当前重点模块 README 是否具备维护型入口信息
4. 检查项目专属坑位文档是否已有落点
5. 确认后续 AI 能从 `docs/README.md -> 项目开发维护索引 -> 模块 README / 坑位文档 / 任务执行卡` 这条链路恢复上下文

## 5. AI 执行规则

如果你是 AI，在长期维护项目里工作时：

1. 先判断项目是否已经进入长期维护阶段
2. 如果文档入口较多、模块较多、项目差异较多，主动检查是否需要补“项目开发维护索引”
3. 可以主动把索引补到可维护状态，但不能把 Human-in-the-loop 审核点删掉
4. 新增索引后，必须同步更新 `docs/README.md` 和相关模块入口
5. 如果沉淀出来的是通用规则，优先回灌到 `base`
6. 如果沉淀出来的是单项目坑位，只留在项目内

## 6. 一句话记住

开发维护索引不是新的知识库，也不是总说明替代品。

它只是给长期维护项目补一层轻量入口，让后续 AI 和新人维护者能更快找到：**先看哪里、再看哪里、哪些是共性规则、哪些是项目私有问题。**

# Cool Project Stack

## 适用范围

- 团队新项目初始化、功能开发、模块扩展、接口联调、设计文档、开发文档、交付说明。
- 模板仓库内存在 `cool-admin-vue`、`cool-admin-midway`、`cool-uni` 作为初始化基线时。
- 需求同时涉及规范判断、代码落点判断、文档输出、阶段化推进时。
- 项目已经进入长期维护阶段，需要先恢复项目理解、再决定是否开发时。
- 需要 Human-in-the-loop 协作，而不是 AI 一口气自动做完全部工作时。
- 需要判断项目是否应该建立“开发维护索引”，并把维护入口补到可持续接手时。
- 需要判断项目是否应该建立“AI 接手入口 / 文档路由入口”，让后续 AI 先找对文档再回答。

## 单一决策清单（先看这个）

先只做 4 个判断，其他细节再往后走。

| 判断项 | L1 | L2 | L3 | L4 |
| --- | --- | --- | --- | --- |
| 怎么判 | 小修复、小改动；只影响单端；不改主流程、不改数据库 | 普通功能；范围可控；通常在单模块内扩展 | 复杂功能/多人协作；跨角色、跨多个页面/接口/目录 | 跨端 / 系统级 / 高影响；涉及核心流程、公共结构、主数据 |
| 是否必须先补文档 | 可不先补完整文档；至少保留简短改动说明 | 默认先进入文档流；至少补需求、技术、实施；仅在任务非常明确且总控判断可跳过时才允许不先补 | 必须先进入文档流 | 必须先进入文档流 |
| 要加载哪些 skill | 本文件 + 对应端 skill | 本文件 + 对应端 skill + `../cool-team-docs/SKILL.md` | 本文件 + 对应端 skill + `../cool-team-docs/SKILL.md` | 先看本文件，再看相关端 skill；同时加载 `../cool-team-docs/SKILL.md` |
| 是否必须等人工确认 | 默认不强制，可直接改 | 默认要；至少在任务分级/影响范围和开发前文档后等确认 | 必须等；文档与步骤拆分确认后再开发 | 必须等；阶段化推进，每步都可验收 |

补充规则：

- `cool-project-stack` 负责判断任务属于哪一级、是否进入文档流、是否允许跳过、是否要分阶段、是否必须等人工确认。
- 一旦确定“进入文档流”，文档落点、命名、README 串联、版本组织、执行卡组织，统一交给 `../cool-team-docs/SKILL.md` 处理；新建文档必须优先沿用当前项目已有命名风格，已有中文编号文档时继续使用中文编号命名，不把英文模板名当默认。
- L2 及以上默认先进入文档流，再开发；是否允许跳过，不由文档 skill 单独决定，而由本 skill 结合任务明确性、影响范围和用户要求判断。
- 只要进入开发前文档产出阶段，必须在开发文档中补《多 Agent 协作计划》或等价章节；如果本次只使用一个 AI，也要写明“本次不拆多 agent”的原因。
- 不能直接开多个 agent 并行乱跑；必须先在开发文档里规划 agent 分工、输入输出、交接顺序、人工确认点，再按阶段执行。
- 如果当前项目存在 `skills/cool-project-stack/SKILL.md`，项目自有 skill 是主流程；Superpowers / 外部规划工具不能单独决定文档结构、任务阶段、开发入口，只能作为阶段 0 草稿或输入材料。

## 这个 skill 现在的默认工作方式

这个 skill 的默认目标，不再只是“接需求后补文档再开发”，而是把整个任务改造成**阶段化执行总控流程**。

但这里的“总控”不是“AI 一次性把所有内容闷头做完”，而是：**AI 可以主动推进、主动补齐、主动发现缺口、主动完善文档和流程；同时严格保留人工审核点，不得越权穿透。**

默认流程是：

1. 需求分析与任务分类阶段
2. 开发前文档产出阶段
3. 文档审核与迭代阶段
4. 分步骤开发阶段
5. 每步验收与纠偏阶段
6. 收尾补齐文档阶段

这 6 个阶段默认按顺序推进，**前一阶段没有完成，不能进入下一阶段**。

其中有些阶段必须等待人工确认：

- 阶段 1 结束后：如果任务不是 L1 小修复，默认等待用户确认任务理解、分级和影响范围
- 阶段 2 结束后：默认等待用户审核开发前文档
- 阶段 3 中：每次文档被修改后，默认继续等待用户确认，没确认前不能进入开发
- 阶段 4 中：每一个开发步骤完成后，默认进入阶段 5 等待人工验收或继续指令
- 阶段 5 中：如果该步存在理解偏差、实现偏差、范围偏差，先回改文档，再继续下一步开发
- 阶段 6 结束后：等待用户确认交付内容是否完整

一句话：**默认是“文档先对齐、步骤分开做、每步可检查、出错先回文档”，不是无人审核的一次性生成。**

## 自主完善机制（在 Human-in-the-loop 边界内）

这个 skill 允许 AI 在**不额外等待指令逐条下发**的前提下，主动把这套流程持续完善下去；但这种“自主”，只发生在**补强流程与产物质量**的方向上，不能替代人工决策。

### 可以自主做的事

1. 主动发现当前流程、文档、模板、检查清单、命名方式里的缺口与歧义。
2. 主动补充开发前文档需要的章节、问题清单、边界说明、风险提示、回退方案、验收点。
3. 主动把一个大步骤继续细分成更适合人工验收的小步骤，并补齐对应执行卡。
4. 主动同步更新上下游文档，避免 README、需求、技术、实施、测试、交付文档彼此脱节。
5. 主动在每一轮完成后提出“下一轮最合理该完善什么”，而不是等用户重新从零组织指令。
6. 主动把执行中发现的偏差沉淀回文档、模板、skill 规则，避免下次再犯同类问题。
7. 主动补齐“如果当前信息不足，至少先输出草案 + 待确认问题”的兜底路径，避免任务卡死。

### 不能自主越过的边界

1. 不能删除或绕过人工审核点。
2. 不能把“需要用户确认”偷偷改写成“AI 自行判断即可”。
3. 不能在文档未确认时，把后续开发当作默认已获批继续推进。
4. 不能用“我已经自主完善过了”代替用户验收。
5. 不能在实现偏差出现后，跳过文档回改直接硬做下一步。

### 默认执行姿势

如果用户表达的是“让这套体系自己越来越完善”，默认按下面方式工作：

1. **先自主完善开发前阶段的产物与规则**，包括需求、技术、实施、测试、任务拆分、检查清单、模板。
2. 到达当前流程规定的人工审核点时，必须停下来，明确告诉用户“这里需要确认”。
3. 一旦某轮获得确认，下一轮可以继续自主准备后续产物或后续步骤，而不是只做用户明确点名的那一句。
4. 如果执行时发现旧文档不足以支撑继续推进，先回改文档，再继续执行。
5. 完成一次任务后，允许顺手把本次暴露出的公共流程问题回灌到 skill、模板、README 或检查清单中。

### 判断标准

好的“自主完善”：**自动补强流程，但不吞掉确认权。**

坏的“自主完善”：**把原本要人拍板的地方，偷偷改成 AI 自己拍板。**

## 新人先做什么

激活后先完成 6 件事：

如果当前任务是“初始化新项目 / 迁移 base 规范包 / 同步 skills 或 docs”，先读取 `./references/migration.md`，不要直接进入普通功能开发流程。

1. 判断当前需求属于 `cool-admin-vue`、`cool-admin-midway`、`cool-uni` 中的哪一端，或是否为跨端任务。
2. 先看当前项目已有结构，再看 `base` 模板，不允许直接跳到“通用最佳实践”。
3. 如果项目已经进入长期维护阶段，或任务属于复杂功能、高影响修改、核心模块修改，先恢复项目理解：
   - 先看 `docs/README.md`
   - 再看 `docs/00-system/AI接手入口.md`（如果项目已经建立）
   - 再看 `docs/00-system/项目开发维护索引.md`（如果项目已经建立）
   - 再看系统说明相关文档
   - 再看“项目与 base 差异”相关文档
   - 再看核心模块或当前模块相关文档
4. 按目标端继续读取相邻子 skill：
   - Vue：`../cool-admin-vue-dev/SKILL.md`
   - Midway：`../cool-admin-midway-dev/SKILL.md`
   - Uni：`../cool-uni-dev/SKILL.md`
5. 只要任务不是 L1 小修复，就继续读取 `../cool-team-docs/SKILL.md`
6. 如果任务涉及核心模块、高风险流程、公共结构，不要直接开发，先做检查，再决定是否进入编码。

如果任务属于“新功能、新模块、新页面流程、新接口、数据库调整、多人协作任务”中的任意一种，默认视为需要前期文档，不能直接跳过文档阶段开始编码。

## 常见任务怎么选 skill

先看你现在要做什么：

| 任务类型 | 先看哪个 skill | 下一步做什么 |
| --- | --- | --- |
| 后端 / 接口 / 实体 / 服务 | `../cool-admin-midway-dev/SKILL.md` | 先找同类模块，再决定是否补 API / 数据库文档 |
| 后台 / CRUD / 表单 / 表格 / 页面 | `../cool-admin-vue-dev/SKILL.md` | 先找同类页面，再决定是否补需求 / 技术 / 实施 |
| Uni / 移动端页面 / 路由 / 登录态 | `../cool-uni-dev/SKILL.md` | 先看页面入口和接口接入方式 |
| 小修复 | 对应端 skill | 先看同类代码，改完走检查清单 |
| 新功能 | 对应端 skill + `../cool-team-docs/SKILL.md` | 先补需求、技术、实施，再进入阶段化开发 |
| 跨端任务 | 先看本文件，再看各端 skill | 默认顺序：Midway → Uni → Vue |
| 不知道还要不要装别的外部 skill | `./references/external-skills.md` | 先看“必装 / 推荐 / 按需” |

一句话判断：

- 只是改一点点：先找对应端 skill
- 只要是新功能：加上文档 skill
- 只要跨两个及以上端：先按跨端任务处理

## 任务分级规则

### L1：小修复

常见情况：

- 改文案、样式、提示语
- 修一个明确的小 bug
- 调整一个小判断、小字段、小接口处理
- 不新增模块，不改主流程，不改数据库

要求：

- 可以直接改代码
- 但也要写清楚改了什么
- 提交前做最小自测
- 如果用户明确要求走阶段化流程，也可以按阶段执行，但通常不强制等待多轮确认

### L2：普通功能

常见情况：

- 新增一个普通页面、表单、列表
- 在一个模块内新增一段业务逻辑
- 新增或调整接口，但范围可控

要求：

- 开发前至少补：需求、技术、实施
- 涉及接口变更：补 API 文档
- 涉及数据库变更：补数据库文档
- 默认先完成文档审核，再开始开发

### L3：复杂功能 / 多人协作任务

常见情况：

- 新模块、新流程、跨角色流程
- 前后端联动明显
- 多人协作、分阶段交付
- 影响多个目录、多个页面、多个接口

要求：

- 需要较完整文档链路
- 至少包括：需求、产品、技术、实施、测试、交付
- 涉及接口必须补 API 文档
- 涉及数据库必须补数据库文档
- 默认拆成多个开发步骤，每步都要可验收

### L4：系统级 / 跨端 / 高影响任务

常见情况：

- 跨端任务
- 登录、权限、核心流程、主数据调整
- 系统结构调整
- 同时影响后端、后台、Uni 中两个及以上端

要求：

- 必须补全套文档
- 必须写清楚各端怎么配合
- 只要有接口变化，必须补 API 文档
- 只要有数据结构或表结构变化，必须补数据库文档
- 交付前必须补联调和交付说明
- 开发前先恢复项目理解，不能只根据当前需求直接改代码
- 如果涉及核心模块、高风险流程、公共结构，先完成检查，再决定是否开发
- 默认强制走“阶段审核 + 分步实施 + 每步验收 + 偏差回改文档”流程

## 长期维护项目附加规则

只要项目已经进入长期维护阶段，处理复杂功能或高影响修改时，必须额外执行下面几条：

1. 不能只看当前需求，必须先恢复项目理解。
2. 恢复项目理解时，优先顺序是：
   - `docs/README.md`
   - `docs/00-system/AI接手入口.md`（如果项目已经建立）
   - `docs/00-system/项目开发维护索引.md`（如果项目已经建立）
   - 系统说明相关文档
   - 项目与 `base` 差异相关文档
   - 核心模块或当前模块相关文档
3. 如果任务涉及核心模块、高风险流程、公共结构，先做检查，再决定是否开发。
4. 如果当前项目已经明显偏离 `base`，优先以当前项目为准，不要机械按 `base` 回退。
5. 回答问题、给方案、开始开发前，都要先恢复项目理解，不要只靠临时上下文。
6. 恢复项目理解完成前，不要进入正式开发阶段。

## 跨端任务处理顺序

默认顺序：

1. 服务端 `cool-admin-midway`
2. 用户端 `cool-uni`
3. 后台端 `cool-admin-vue`

原因：

- 服务端接口和数据结构要先稳定
- 移动端通常先依赖服务端接口
- 后台端更多是管理、运营、配置与验证入口

如果任务只涉及单端，则只读取对应子 skill，不要一次性加载全部细节。

## Superpowers / 外部规划工具产物接管机制

当当前项目存在 `skills/cool-project-stack/SKILL.md` 时，项目自有 skill 是主流程。Superpowers 或其他外部规划工具可以提供草稿，但不能单独决定文档结构、任务阶段、开发入口。

常见 Superpowers 产物包括：

- `task_plan.md`
- `findings.md`
- `progress.md`
- `v*-task-card.md`

接管映射：

- `task_plan.md` → 当前项目标准任务执行卡的阶段计划 / 下一步动作
- `findings.md` → 当前项目标准需求说明 / 技术设计 / 调研结论 / 风险记录
- `progress.md` → 当前项目标准任务执行卡的阶段进度 / 已完成内容
- `v*-task-card.md` → 统一迁移 / 修正为项目自有任务执行卡格式

接管步骤：

1. 识别模块 / 版本，确认外部产物应该归入哪个 `docs/01-modules/模块名/` 或 `docs/tasks/` 落点。
2. 合并内容到当前项目风格的标准中文命名文档或任务执行卡，不沿用外部工具自定义流程作为开发入口。
3. 补齐 Codex 多 Agent 协作计划，写清 agent 分工、输入输出、依赖顺序、人工确认点和冲突处理。
4. 补允许修改文件边界和执行记录表。
5. 把执行卡状态标记为“待确认”，等待用户确认后再进入开发。

接管完成后：

- 原始 Superpowers 文件不要继续作为开发入口。
- 标准入口必须是当前项目已有命名风格下的正式文档；如果项目已有中文编号文档，新入口必须使用中文编号文件名。
- 建议移动到 `docs/.superpowers-archive/`，或在标准任务执行卡中标记“已接管”。
- 不要直接删除原始文件。
- 如果 Superpowers 产物与项目自有文档冲突，以项目自有 skill 流程和用户确认后的标准文档为准；冲突内容进入待确认问题。

## 团队首次使用初始化

如果是团队第一次使用这套基座，或者当前环境还没装团队约定的外部 skill，先做下面几步：

1. 读取 `./references/external-skills.md`
2. 先安装“必装”部分
3. 确实需要对应能力时，再安装“推荐”或“按需”部分
4. 如果要一次性安装默认清单，再执行 `bash skills/cool-project-stack/scripts/install-team-skills.sh`
5. 重启 Codex，让新安装的 skill 生效
6. 如果后续真要用 `browser-use`，再执行 `browser-use doctor`
7. 如果后续真要用 `notebooklm`，再按其 skill 说明完成认证和 notebook 配置

注意：

- 这些外部 skill 默认安装到个人 AI 环境中，不安装到每个项目仓库里
- `base/skills` 负责约定“什么时候该调用什么 skill”，不是把第三方 skill 复制进项目
- 不要给新人“第一次就全部装完”的压力

## 外部 Skill 调用时机

完整安装说明和触发矩阵见 `./references/external-skills.md`，常用规则如下：

- 需要搜索、补装、升级其他 skill 时，调用 `find-skills`
- 需求复杂、跨端、多文档、多阶段、多人协作时，优先调用 `planning-with-files`
- 需要做品牌页、专题页、落地页、强视觉页面，且希望去掉 AI 塑料感时，调用 `frontend-design`
- 需要更强的视觉提案、品牌调性、UI/UX 打磨时，调用 `ui-ux-pro-max`
- 需要浏览器自动化、录制流程、截图验收、多步骤联调时，调用 `browser-use`
- 需要从大量文档、资料、知识库中做带来源的研究时，调用 `notebooklm`
- 需要从顶级专家视角做产品、架构、策略破局时，调用 `best-minds`

例外规则：

- 现有项目已经有稳定设计系统或后台风格时，不默认调用 `frontend-design` 和 `ui-ux-pro-max` 去重做视觉语言
- 标准后台 CRUD、普通表单页、简单修复任务，不因为“能设计”就强行触发高视觉 skill

## 规范优先级

规范冲突时，必须按下面的顺序判断，并在回答中说明“本次依据是什么”：

1. 用户当前明确提出的要求
2. 当前项目中已经存在的代码结构、命名方式、规则文件、实现方式
3. `base` 模板中的同类实现
4. 官方文档
   - `https://vue.cool-admin.com`
   - `https://node.cool-admin.com`
   - `https://uni-docs.cool-js.com`
5. 团队级参考 `./references/base-repo-conventions.md`
6. 通用工程最佳实践

注意：

- 团队级参考是补充说明，不覆盖当前项目已有规则。
- `cool-uni` 没有本地 `.cursor/rules` 时，优先级变成：用户要求 > 当前项目代码 > `cool-uni` 模板 > 官方文档 > 团队级参考 > 最佳实践。
- 命名规则优先参考 `./references/naming-conventions.md`，其中项目已有文档命名风格优先级最高；已有中文编号文档时，新建模块文档继续使用中文编号命名。
- 代码组织、模块复用、中文注释要求优先参考 `./references/code-organization.md`

## base 基线

把下面三套模板视为默认初始化基线：

- Vue 基线：`../../cool-admin-vue`
- Midway 基线：`../../cool-admin-midway`
- Uni 基线：`../../cool-uni`

处理新项目时：

- 如果当前项目和 `base` 一致，直接沿用 `base` 风格继续扩展。
- 如果当前项目已经偏离 `base`，优先尊重当前项目已有实现，不强行改回模板。
- 如果当前项目某类功能还没实现，优先参考 `base` 中最接近的结构和写法。
- 只要发现当前项目与 `base` 存在明显差异，先确认差异原因和当前项目约束，再决定是否参考 `base`。

## 默认阶段化工作流

下面这部分是本 skill 的核心流程。默认按阶段推进，不要跳步。

### 阶段 1：需求分析与任务分类

先输出以下内容，再决定要不要继续：

- 需求理解
- 目标端识别
- 任务等级（L1 / L2 / L3 / L4）
- 影响范围
- 模块落点
- 关键文件路径
- 依赖的现有模块或页面
- 风险点和待确认点
- 当前项目是否已经偏离 `base`
- 本次先依据了哪些系统说明、差异记录、模块文档

阶段动作：

1. 先判断任务落在哪些端。
2. 先看当前项目已有结构，再看 `base`。
3. 长期维护项目先恢复项目理解。
4. 给出任务分级和原因。
5. 列出是否需要开发前文档。
6. 只要任务需要走阶段化流程，就创建或初始化任务执行卡，先记录任务名称、当前阶段、任务等级、涉及端、需求摘要、待确认点、下一步动作。

默认确认规则：

- L1 小修复：如果需求非常明确，可直接进入开发或最小文档补充
- L2 / L3 / L4：默认等待用户确认需求理解、任务分级、影响范围后，再进入阶段 2
- 已创建任务执行卡的任务，在等待确认时要把执行卡状态更新为“待确认”

### 阶段 2：开发前文档产出

先确认文档根目录：

- 当前任务发生在模板仓库 `base` 目录内，默认输出到 `base/docs`
- 当前任务发生在具体业务项目中，默认输出到项目根目录 `docs`
- 如果任务是多期迭代功能，文档默认收敛到同一个模块目录 `docs/01-modules/模块名/`，由模块 `README.md` 统一维护版本规划、阅读顺序、当前版本入口和长期约束入口

项目级长期文档处理规则：

- 如果文档导航 `docs/README.md` 不存在，先补
- 如果项目级 `系统说明文档` 不存在，先补
- 如果项目已经进入长期维护阶段，复杂功能或高影响修改开始前，先看系统说明文档、项目与 `base` 差异文档、核心模块相关文档
- 如果任务涉及核心模块、高风险流程、公共结构，开发前先完成检查，不要直接进入编码
- 如果本次新增了模块、页面入口、角色流程、外部依赖或部署约定，开发完成后必须同步更新 `系统说明文档`
- 如果本次新增、确认或扩大了项目与 `base` 的差异，开发完成后必须同步更新差异记录
- 如果本次新增或变更了可被业务、测试、运营直接使用的功能，开发完成后必须同步更新 `系统功能说明文档`
- 如果本次新增了模块，或明显扩展了模块现有能力，开发完成后必须同步更新对应模块 `README.md`、模块能力说明或模块清单，让后续人和 AI 能快速知道这个模块已经具备什么能力、哪些文件可以复用

以下文档是开发前的标准产物，不要等到开发完成后才补：

- L2：至少补 `需求说明文档`、`技术设计文档`、`开发实施文档`
- L3 / L4：至少补 `需求说明文档`、`产品设计文档`、`技术设计文档`、`开发实施文档`
- 只要进入开发前文档产出阶段，必须在 `开发实施文档` 或任务执行卡中写《多 Agent 协作计划》；如果另有单独协作计划文档，也要在开发实施文档中链接到它

按场景追加：

- 涉及新表、改表、字段变更、索引、状态字段、数据迁移：必须补 `数据库设计文档`
- 涉及前后端联调、新接口、接口字段调整：必须补 `接口与数据结构说明`
- 涉及复杂页面流程、角色流程、状态流转：在技术设计或开发实施文档中写清页面流程与状态流转

阶段动作：

1. 先产出开发前文档。
2. 再拆出推荐开发步骤。
3. 标记每一步的目标、边界、验收点。
4. 写清《多 Agent 协作计划》，至少包含：Codex agent 角色、触发条件、适用阶段、输入文档、输出物、上下文范围、依赖顺序、人工确认点、冲突 / 返工处理。
5. 写清楚哪些点仍待用户确认。
6. 把开发前文档清单、当前结论、待确认问题、下一步动作同步到任务执行卡。

多 Agent 默认建议：

- 默认使用 Codex 推进开发；不是设置其他 AI 主导架构。
- 当任务达到一定复杂度或阶段需要时，在开发前文档里规划 Codex 多 agent 协同。
- 不拆的情况：L1 小改、单文件低风险、上下文很小、用户明确只要一个 agent。
- 必须考虑拆的情况：L2+、跨端 / 跨模块、接口 + 前端 + 数据库同时变化、多阶段迭代、高风险重构、测试或审查需要独立视角。
- 可拆的方向包括：需求 / 文档审查 agent、实现 agent、测试补齐 agent、代码审查 agent、重构 agent、回归验证 agent 等；角色名称不强制固定，可按任务调整。
- 每个 agent 只拿必要上下文，不把完整项目、全部文档、无关历史一次性塞给所有 agent。
- 多 agent 可以按依赖串行或有限并行，但不能在没有协作计划、没有交接边界、没有人工确认点时直接同时开跑。
- 每个 Codex agent 必须写清允许修改文件 / 目录；没有列入允许范围的文件不能改。
- 开发过程中允许二次拆分 Codex agent，但必须先更新任务执行卡或协作计划，再启动新 agent。

默认确认规则：

- 阶段 2 结束后，默认必须等待用户审核文档
- 用户没有确认前，不能进入阶段 4 开发
- 等待审核时，要把任务执行卡状态更新为“待确认”

### 阶段 3：文档审核与迭代

这个阶段的目标不是“快速跳过”，而是让文档真正可执行。

阶段动作：

1. 用户审核需求、方案、步骤拆分。
2. AI 根据问题或反馈回改文档。
3. 每次改完都重新同步受影响文档。
4. 确认“文档版本”和“接下来要开发的步骤”已经一致。
5. 每次文档有回改时，同步更新任务执行卡里的当前结论、待确认问题、下一步动作、相关文档清单。

默认确认规则：

- 文档每次被修改后，默认继续等待用户确认
- 没有明确确认“可以开发”，不能进入阶段 4
- 等待再次确认期间，任务执行卡状态保持为“待确认”

文档回改要求：

- 如果需求理解变了，要回改：需求说明文档、产品设计文档、开发实施文档
- 如果接口或字段变了，要回改：技术设计文档、接口与数据结构说明、数据库设计文档（如有）
- 如果步骤顺序变了，要回改：开发实施文档、测试检查项、交付说明草稿
- 如果影响范围扩大或缩小，要回改：需求说明文档、技术设计文档、系统说明文档相关章节（如已写）

### 阶段 4：分步骤开发

满足以下条件后才能进入编码阶段：

- 已明确本次功能属于哪一端
- 已完成任务分级
- 已核对当前项目与 `base` 中的同类实现
- 长期维护项目下，已恢复系统说明、项目与 `base` 差异、核心模块相关文档这三类理解
- 已完成最少必需文档
- 已完成《多 Agent 协作计划》或等价章节，并明确 Codex agent 角色、触发条件、上下文范围、依赖顺序和人工确认点
- 关键接口、关键字段、关键页面入口没有悬空
- 文档已获用户确认
- 如果涉及核心模块、高风险流程、公共结构，已先完成检查

如果文档仍有明显空白项，只能继续补文档或补澄清，不能直接开始写代码。

开发约束：

- 不发明仓库里不存在的目录体系。
- 先检查命名是否符合 `./references/naming-conventions.md`
- 代码组织、模块拆分、模块复用、中文注释要求，先检查是否符合 `./references/code-organization.md`
- 新增代码前先检查当前项目和 `base` 是否已有同类模块、相近页面、可复用组件、可复用 service、可复用 hooks、可复用工具方法，能复用优先复用，不能复用再新增。
- 新增模块或明显扩展模块能力时，开发完成后必须同步更新模块 README、功能说明或模块清单，让后续 AI 能快速知道现有能力和可复用入口。
- 关键业务逻辑、状态流转判断、核心字段含义、特殊兼容处理、复用关系等位置，必须补清晰明了的中文注释，让初级程序员能看懂“这里为什么这么写”。
- 不把页面逻辑、业务逻辑、接口调用、类型定义、配置常量等大量逻辑堆进单个文件；页面 / service / hooks / utils / types / constants 等职责应按模块和职责拆分。
- 后端也不能把全部逻辑塞进单个 service 或 controller；controller 负责请求入口，service 负责业务编排，复杂规则、状态处理、公共能力要按职责拆分。
- 不把其他技术栈的习惯硬套进当前端。
- 不为了“看起来高级”而过度抽象。
- 缺少必要信息时，只问会影响落地的最小问题。
- 尽量复用 `base` 和当前项目已有模块，不轻易新增第二套模式。
- 必须按文档中约定的步骤开发，不要一口气做完整包。

开发方式：

1. 每次只推进一个明确步骤。
2. 每个步骤完成后，输出本步改动、影响范围、待验收点。
3. 同步更新任务执行卡中的已完成内容、当前阶段、当前状态、下一步动作。
4. 默认进入阶段 5，等待人工验收或继续指令。

开发过程中二次拆分 Codex agent 规则：

1. 允许开发过程中二次拆分 agent，例如多个后端 agent 分别开发 A / B / C 模块；默认总数控制在 **2-5 个 Codex agent**。超过 5 个时，不继续增加并行 agent，而是拆成多个阶段分批执行。启动前必须先更新任务执行卡 / 协作计划，记录新增 agent、触发原因、输入上下文、允许修改文件 / 目录、下一步交接对象和状态。
2. 拆分前必须确认模块 / 文件边界：每个 agent 都要有明确允许修改文件清单，不能只写“后端”“后台”“某模块”这种模糊范围。
3. 不允许两个 agent 同时改同一文件。
4. 公共类型、路由、菜单、权限配置、数据库 migration、共享工具、公共枚举、全局常量等共享文件，必须单独列为共享变更，由单独 agent 或串行步骤处理。
5. 接口、DTO、枚举、事件、数据库字段、状态值、权限标识等跨模块契约必须先冻结，再允许 A / B 模块并行。
6. 如果某个 agent 发现必须改边界外文件，必须停止并回报原因、建议修改文件和影响范围，不能自行扩大范围。
7. 推荐合并顺序：共享契约 / 基础改动 → 各模块 agent 按依赖顺序合并 → 集成检查 / 回归验证。
8. 只支持有限并行：互不重叠的模块实现可以并行；同一代码区域、同一共享文件、基于旧实现写测试、依赖未冻结接口写前端等场景禁止并行。

### 阶段 5：每步验收与纠偏

这个阶段用于把“写完一段代码”变成“确认这一段做对了”。

阶段动作：

1. 对照本步文档目标检查实现是否一致。
2. 对照验收点检查代码、接口、页面、状态流转。
3. 由人工确认是否通过、是否继续下一步。
4. 如果发现理解错误、范围错误、步骤错误，先回改文档，再改代码。

默认确认规则：

- 每个开发步骤完成后，默认等待用户验收
- 用户未确认通过前，不进入下一步开发
- 等待验收时，任务执行卡状态更新为“待确认”；验收通过后，再更新为下一阶段对应状态

纠偏规则：

- 如果只是实现细节偏差：先回改当前步骤相关的开发实施文档，再调整代码
- 如果是需求理解偏差：回到阶段 3，先回改需求与设计文档
- 如果是接口、字段、状态定义偏差：先回改技术设计、API、数据库文档，再调整代码
- 如果某一步被推翻：至少回改该步对应的开发实施文档、测试检查项、交付说明，并检查前序文档是否也被影响，同时在任务执行卡里补齐“被推翻原因、已回改文档、下一步动作”

一致性要求：

- 文档和代码要始终保持一致
- 不能出现“文档还是旧的，代码已经改成新的”
- 不能出现“代码回滚了，但文档还保留旧结论”

### 阶段 6：收尾补齐文档

开发结束后，不是直接宣布完成，而是进入收尾阶段。

阶段动作：

1. 补齐测试、联调、交付文档。
2. 同步更新 `docs/README.md` 中新增模块、阅读顺序或文档入口。
3. 同步更新 `系统说明文档` 中受影响的章节。
4. 同步更新 `系统功能说明文档` 中新增或变更功能的入口、流程、限制条件、权限要求。
5. 检查开发前文档、代码实现、测试记录、交付说明是否一致。
6. 把最终结论、最终产物、收尾结果同步到任务执行卡，并把状态更新为“已完成”或“已暂停”。

默认确认规则：

- 阶段 6 结束后，等待用户确认交付内容是否完整

收尾产物：

- 改动说明
- 测试与联调记录
- 已知风险
- 后续优化项
- 更新后的文档入口

文档输出规则与模板由 `../cool-team-docs/SKILL.md` 负责。

## 阶段切换硬规则

为了避免 AI 直接跳步，默认遵守下面规则：

1. 没做任务分级，不进入开发前文档阶段。
2. 该补的开发前文档没补齐，不进入开发阶段。
3. 开发前文档没有写清《多 Agent 协作计划》或等价章节，不进入开发阶段。
4. 用户没确认文档，不进入开发阶段。
5. 当前步骤没验收，不进入下一开发步骤。
6. 需求、接口、字段、流程被推翻时，先回改文档，再继续开发。
7. 文档和代码不一致时，优先先修一致性，再继续推进。
8. 长期维护项目里，没恢复项目理解前，不进入正式开发。

## 停止条件 / 不要继续往下做

出现下面任意情况时，不要继续往下补文档或补代码，先把断点补齐：

1. `docs/README.md`、模块 `README.md` 或当前阶段依赖的入口文档已经失效、缺链或与现状冲突时，不要继续新增后续文档；先修入口，再继续。
2. 已进入多期模块文档流，但模块 `README.md` 还没串起版本关系、阅读顺序、当前版本入口时，不算文档组织完成；不要继续宣布阶段完成。
3. 当前版本文档已更新，但 README 没回写当前版本状态、版本入口或推荐阅读顺序时，不算阶段收口完成；不要继续往下推进到“已完成”。
4. 文档导航、模块 README、版本文档、执行卡四者之间出现互相对不上的情况时，不要继续开发下一步；先修一致性。
5. 开发前文档还有关键空白项：接口未定、字段未定、主流程未定、端之间依赖未定时，不要继续写代码。
6. 当前步骤验收结论、执行卡状态、文档状态三者没同步时，不要继续进入下一步骤。
7. 需要进入文档流但还没加载 `../cool-team-docs/SKILL.md` 时，不要自行发明文档落点和命名规则。

- 全部使用中文。
- 优先写给初级程序员看懂。
- 少用空泛术语，多用“先做什么、再做什么、放哪里、怎么做、注意什么”。
- 文件路径、模块名、页面名、接口名尽量写清楚。
- 说明阶段时，优先给出“当前在哪一阶段、下一步要等什么确认”。

## 完成标准

一次任务完成时，至少满足以下条件：

- 已明确本次采用的规范来源。
- 已明确任务等级和对应文档要求。
- L2 及以上任务的开发前文档已包含《多 Agent 协作计划》或等价章节。
- 代码落点和结构与当前项目或 `base` 保持一致。
- 开发前文档阶段没有被跳过。
- 重要设计决策有说明。
- L2 及以上任务已包含对应的前期文档、联调文档和交付说明。
- 每个关键开发步骤都具备可验收结果。
- 如果某一步被推翻，相关文档已经同步回改。
- 文档与代码保持一致。
- 如果存在阻塞，已明确阻塞点、影响范围和下一步最小动作。

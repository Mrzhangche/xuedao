# Cool Team Docs

## 职责边界（先看这个）

`cool-team-docs` 只负责**已经进入文档流之后**的文档组织与产出，不负责任务总控判断。

明确边界：

- 任务属于 L1 / L2 / L3 / L4 哪一级：由 `../cool-project-stack/SKILL.md` 判断
- 是否必须先补文档、是否允许跳过文档：由 `../cool-project-stack/SKILL.md` 判断
- 是否需要分阶段执行、是否必须等人工确认：由 `../cool-project-stack/SKILL.md` 判断
- 一旦确认进入文档流：文档落点、命名、README 串联、版本文档组织、执行卡组织，由本 skill 负责
- 开发前文档中的《多 Agent 协作计划》或等价章节，由本 skill 按总控分级和阶段要求补齐；是否真的启用多个 agent、何时启用，由总控和用户确认决定

你可以引用分级结果来决定最少文档集，但不要在这里重复承担任务总控角色。

## 何时使用

- 新模块
- 新页面流程
- 新接口
- 新表、改表、字段调整、索引调整
- 初始化配置
- 多人协作任务
- 用户明确要求输出设计文档或开发文档

简单修复可以只输出简短说明；L2 及以上任务要使用模板化文档。
只要任务已经由 `../cool-project-stack/SKILL.md` 判定进入文档流，且属于“新功能”而不是单点修复，本 skill 默认在编码前先完成对应文档组织与产出。

## 先做什么

1. 先确认这次任务是否已经由 `../cool-project-stack/SKILL.md` 判定为进入文档流
2. 再根据已给出的 L1 / L2 / L3 / L4 结果，决定最少要补哪些文档
3. 先把文档落点和命名定住
4. 检查 README、版本文档、执行卡怎么串起来
5. 文档组织够了再进入正式开发
6. 只要进入开发前文档产出阶段，就补《多 Agent 协作计划》或等价章节；如果本次不拆多 agent，也要写清原因和后续触发条件

## 在 Human-in-the-loop 下的自主补文档规则

这个 skill 默认允许 AI **主动把文档链路补完整、补清楚、补到可审核**，而不是等用户一条一条指定“再补哪份文档”。

但这里的“自主”，只表示**自主完善文档产物**，不表示可以越过文档审核点直接把后续开发视为已批准。

### 可以自主做的事

1. 主动判断当前任务还缺哪些文档、模板、版本入口、README 串联。
2. 主动补齐文档章节，例如边界、风险、依赖、回退方案、验收标准、待确认问题。
3. 主动把一份过大的文档拆成更适合团队阅读和审核的多份文档。
4. 主动同步 README、版本文档、执行卡、检查清单之间的链接和说明。
5. 主动把“文档里说不清”的地方整理成待确认问题，集中抛给人工审核。
6. 主动在每轮审核后，把反馈回灌到对应文档，而不是只改某一份表面文档。
7. 主动补“草案版 + 待确认问题”作为兜底输出，避免因为信息不全而完全卡住。

### 不能越过的边界

1. 文档产出完成，不等于文档已确认。
2. AI 可以先把文档补到可审，但不能把“待审核”当成“已批准”。
3. 如果 `cool-project-stack` 要求当前阶段停在文档审核，这里就必须停。
4. 如果审核反馈推翻了某些结论，要先改文档，再允许进入后续开发。

### 默认执行方式

1. 先产出当前阶段所需的最小完整文档集。
2. 再主动检查是否缺 README 串联、版本入口、执行卡、接口文档、数据库文档。
3. 如果缺，就顺手补齐到“团队可以审”的程度。
4. 然后明确标出：哪些内容已经写完，哪些问题还在等确认。
5. 在确认前，不把文档完成误报成“任务已经可以直接开发完毕”。

## Superpowers / 外部规划工具产物接管

如果当前项目存在 `skills/cool-project-stack/SKILL.md`，文档流必须服从项目自有 skill。看到 Superpowers / 外部规划工具生成的文件时，不要直接继续它的流程，先按阶段 0 草稿接管。

常见 Superpowers 产物：

- `task_plan.md`
- `findings.md`
- `progress.md`
- `v*-task-card.md`

接管映射：

- `task_plan.md`：合并到当前项目标准任务执行卡的阶段计划 / 下一步动作
- `findings.md`：按内容归入需求说明、技术设计、调研结论或风险记录
- `progress.md`：合并到当前项目标准任务执行卡的阶段进度 / 已完成内容
- `v*-task-card.md`：迁移 / 修正为项目自有任务执行卡格式

接管动作：

1. 先识别模块 / 版本，确定落点。
2. 把外部内容合并到当前项目风格的标准中文命名文档或任务执行卡。
3. 补齐 Codex 多 Agent 协作计划。
4. 补允许修改文件边界和执行记录表。
5. 把执行卡状态标记为“待确认”。
6. 原始文件移动到 `docs/.superpowers-archive/`，或在执行卡中标记“已接管”；不要直接删除。

如果外部产物与项目自有文档冲突，以项目自有 skill 流程和用户确认后的标准文档为准；冲突内容写入待确认问题。

## AI 接手入口 / 文档路由入口规则

如果团队明确希望“任何 AI 接手时，先找对文档再回答”，或者项目已经进入长期维护且正式文档入口较多，默认要检查是否需要补一份 `docs/00-system/AI接手入口.md`。

### 这份文档解决什么问题

它主要解决：

- 用户问的是功能、进度、代码落点、设计原因还是项目特有坑，AI 容易混着答
- 项目文档多了以后，只看 `docs/README.md` 还不够快
- 后续 AI 容易直接扫代码、直接套流程，没先找对正式文档

一句话：它是接手时的文档路由入口。

### 它和其他文档的关系

- `docs/README.md`：项目总入口，负责全局导航
- `AI接手入口.md`：接手分流入口，负责先判断问题类型，再路由到正式文档
- `项目开发维护索引.md`：长期维护导航，负责说明常见开发动作和文档层级关系
- 模块 `README.md`：模块正式入口，负责模块背景、版本规划、当前版本、长期约束、代码落点
- 项目专属坑位文档：负责项目私有坑和兼容点
- 任务执行卡：负责当前任务 / 当前版本推进状态

### AI 默认动作

1. 先看 `docs/README.md`
2. 如果项目已建立 `docs/00-system/AI接手入口.md`，再看它
3. 先按问题类型跳到对应正式文档
4. 确认依据后，再回答或再改代码
5. 不要把这份入口文档误用成知识库

### 不要误用成下面两件事

- 不是默认每次都触发更重流程或 superpowers
- 不是默认每次都完整走 docs-first / project-stack
- 它只负责“先找对文档再回答”
- 是否进入完整 docs → review → dev，仍由 `../cool-project-stack/SKILL.md` 判断



如果项目已经进入长期维护阶段，并且文档入口已经不止一层，默认要检查是否需要补一份 `docs/00-system/项目开发维护索引.md`。

### 什么情况下要补

满足下面任一条，建议补：

- 项目已有较多正式文档，新人或后续 AI 不容易快速找到入口
- 项目已有系统文档、模块 README、项目专属坑位文档、任务执行卡并存
- 项目已经和 `base` 产生实际差异，需要明确“共性规则”和“项目私有问题”的分层入口
- 项目已经进入长期维护，而不是一次性开发后就结束

### 这份索引至少要回答什么

1. 正式文档入口有哪些
2. 通用规则看哪里
3. 项目私有坑 / 兼容记录看哪里
4. 当前重点模块入口有哪些
5. 常见开发动作先看哪里
6. 哪些经验应回灌 `base`，哪些只留项目内

### 和其他文档的关系

- `docs/README.md`：项目文档总入口，要给开发维护索引留入口
- 模块 `README.md`：模块级正式入口，要负责模块背景、阅读顺序、当前版本、代码落点、长期约束、常见修改入口
- 项目专属坑位文档：记录项目私有坑，不要把全文复制进索引
- 任务执行卡：记录任务当前推进状态，不替代长期入口

### AI 默认动作

1. 判断项目是否需要开发维护索引
2. 如果需要，先补 `docs/00-system/项目开发维护索引.md`
3. 再同步更新 `docs/README.md`
4. 再检查当前重点模块 `README.md` 是否已经具备维护型入口信息
5. 保持轻量索引层，不把它写成知识库

## 文档风格

- 全部使用中文
- 优先写给初级程序员
- 少用抽象词，多用“做什么、为什么、放哪里、怎么做、注意什么”
- 一份文档只解决一类问题，不把所有内容混在一起

### 文档命名优先级（硬规则）

新建项目文档时，命名优先级必须高于模板默认示例：

1. **最高优先级：当前项目已有文档命名风格**。
2. 如果当前项目已有中文编号命名，例如 `01-新人先看.md`、`03-功能开发怎么走.md`、`07-任务执行卡模板.md`，则模块文档也必须优先继续使用中文编号命名。
3. `base` / skill 里出现的英文文件名只能作为旧格式兼容或外部工具产物识别，不能作为新建项目文档的默认命名。
4. Superpowers 生成的英文文件名要被接管、合并或归档，不要继续沿用为标准文件名。
5. 如果接管后需要归档，归档路径可使用 `docs/.superpowers-archive/`；标准入口必须是当前项目风格的中文命名文档。

中文编号命名项目里，推荐模块版本目录使用：

- `README.md`
- `长期约束说明.md`
- `核心实体说明.md`
- `v0.1/00-任务执行卡.md`
- `v0.1/01-需求说明.md`
- `v0.1/02-产品设计.md`
- `v0.1/03-技术设计.md`
- `v0.1/04-数据库设计.md`
- `v0.1/05-接口说明.md`
- `v0.1/06-开发实施.md`
- `v0.1/07-测试清单.md`
- `v0.1/08-交付说明.md`

例如当前项目已有 `docs/01-新人先看.md`、`docs/02-功能开发怎么走（超短版）.md`、`docs/checklists/核心模块修改前检查.md` 时，新模块应优先使用 `docs/01-modules/学习内容与权限系统/v0.1/00-任务执行卡.md` 这类中文编号文件名。

旧英文名只允许写在“旧格式识别 / 兼容”段落里，用于说明 `v0.1-requirements.md`、`v0.1-implementation.md`、`v0.1-task-card.md` 等是待接管 / 待迁移对象，不是新文件默认名称。

## 多 Agent 协作计划写法

只要任务进入开发前文档产出阶段，默认必须在 `开发实施文档`、任务执行卡，或单独协作计划文档中写《多 Agent 协作计划》。如果写成单独文档，`开发实施文档` 必须链接到它。

这份计划解决的是：**先规划 agent 分工与交接，再按阶段执行**。不能直接开多个 agent 并行乱跑。

### 至少要写清楚的字段

每个参与角色 / agent 至少写清：

1. **Codex agent 角色 / agent 名称**：例如“需求 / 文档审查 agent”“实现 agent”“测试补齐 agent”“代码审查 agent”“重构 agent”“回归验证 agent”；名称不强制固定，可按任务调整。
2. **触发条件**：什么任务级别、影响范围或阶段状态下才启动它；如果不拆，也要写明原因。
3. **适用阶段**：需求拆解、技术设计、代码实现、局部重构、测试补齐、代码审查、验收等。
4. **输入文档**：它要读取哪些需求、设计、接口、数据库、执行卡或代码片段。
5. **输出物**：它要产出代码、测试、审查意见、文档回改建议，还是验收结论。
6. **上下文范围**：只给必要上下文，例如某个模块目录、某份接口文档、某几个文件；不要默认把全项目和全部历史都塞进去。
7. **依赖顺序**：先等谁完成，谁可以并行，谁必须等人工确认后再启动。
8. **人工确认点**：在哪些节点必须停下来让用户确认，例如文档确认、接口冻结、阶段验收、审查问题是否采纳。
9. **冲突 / 返工处理**：多个 agent 结论冲突、实现偏离文档、测试推翻设计时，先回到哪份文档，谁负责整理差异，谁确认后再继续。

### Codex 多 Agent 默认建议

默认使用 Codex 推进开发；不是设置其他 AI 主导架构。进入开发前文档产出阶段时，要先判断是否需要 Codex 多 agent 协同，并把分工写进计划。

需要明确告诉 Codex 何时拆多个 agent：

- **不拆的情况**：L1 小改、单文件低风险、上下文很小、用户明确只要一个 agent。
- **必须考虑拆的情况**：L2+、跨端 / 跨模块、接口 + 前端 + 数据库同时变化、多阶段迭代、高风险重构、测试或审查需要独立视角。
- **可拆的方向**：需求 / 文档审查、代码实现、测试补齐、代码审查、重构、回归验证等；角色名称不固定，按任务目标调整。
- 不是同时乱开多个 Codex；要先在文档里规划，按依赖串行或有限并行，每个 agent 只拿必要上下文。

### 推荐模板

```md
## 多 Agent 协作计划

### 协作原则

- 先确认文档和任务边界，再启动 agent。
- 每个 agent 只拿完成本阶段所需的最小上下文。
- 不直接并行乱跑；并行前必须明确输入、输出、依赖和合并方式。
- 发现冲突或返工时，先回改文档和执行卡，再继续开发。
- 每个 Codex agent 必须有明确的允许修改文件 / 目录；没有写进允许范围的文件不能自行修改。
- 发现必须改边界外文件时，agent 必须停止并报告，不能自行扩大范围。

### Agent 分工表

| Codex agent 角色 / agent 名称 | 触发条件 | 适用阶段 | 输入文档 | 输出物 | 上下文范围 | 允许修改文件 / 目录 | 依赖顺序 | 人工确认点 | 冲突 / 返工处理 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Codex 需求 / 文档审查 agent | L2+ 或需求、接口、流程仍需独立检查 | 需求拆解、文档组织、任务边界检查 | 需求说明、技术设计、开发实施、任务执行卡 | 文档问题清单、阶段边界、回改建议 | 开发文档和必要代码入口 | 仅允许修改本次文档和执行卡；不改业务代码 | 先于实现 agent；启动实现前先确认边界 | 文档审核、阶段验收 | 汇总差异，先回改文档再安排返工 |
| Codex 实现 agent | 文档已确认且进入具体编码步骤 | 代码实现、局部重构 | 已确认的开发实施、接口说明、目标文件 | 代码改动、必要说明 | 目标模块目录和相关同类实现 | 只允许修改本步骤列出的目标文件 / 目录 | 文档确认后启动；依赖接口和字段冻结 | 实现完成后验收 | 偏离文档时停止扩写，回交文档审查 agent 整理 |
| Codex 测试 / 审查 agent | 实现完成后需要独立测试或审查视角 | 测试补齐、代码审查 | 实现 diff、测试清单、验收点 | 测试补充、审查问题清单 | 本次改动文件和测试入口 | 只允许修改指定测试文件；审查 agent 默认不改代码 | 实现完成后启动 | 审查问题是否采纳 | 问题影响设计时回到技术设计或实施文档 |
```

### 执行记录表（写进任务执行卡）

任务执行卡必须能记录开发中新增的 agent 和每次交接。只要启动、交接、暂停、采纳或驳回某个 Codex agent 结论，就补一行：

```md
| agent 名称 | 启动阶段 | 触发原因 | 输入上下文 | 允许修改文件 / 目录 | 实际修改文件 | 输出结论 | 是否采纳 | 是否触发文档回改 | 下一步交接对象 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Codex 需求 / 文档审查 agent | 阶段 2 | 开发前独立检查边界 | 需求、技术设计、执行卡 | docs/01-modules/xxx/ | docs/01-modules/xxx/v0.1/06-开发实施.md | 发现接口字段待冻结 | 是 | 是 | Codex 实现 agent | 已完成 |
```

### 开发过程中二次拆分 Codex agent 规则

允许在开发过程中二次拆分 Codex agent，例如后端 A 模块、B 模块、C 模块分别交给不同实现 agent。默认总数控制在 **2-5 个 Codex agent**；超过 5 个时，不继续增加并行 agent，而是拆成多个阶段分批执行。二次拆分前必须先满足这些条件：

1. **先更新任务执行卡 / 协作计划**：不能口头决定后直接开新 agent；先记录新增 agent、触发原因、输入上下文、允许修改文件 / 目录、交接对象和状态。
2. **先确认模块 / 文件边界**：每个 agent 都要有明确允许修改文件清单；不能只写“后端模块”这种模糊范围。
3. **禁止同时改同一文件**：两个 agent 不允许并行修改同一个文件。
4. **共享文件单独处理**：公共类型、路由、菜单、权限配置、数据库 migration、共享工具、公共枚举、全局常量等共享文件，必须单独列为共享变更，由单独 agent 或串行步骤处理。
5. **跨模块契约先冻结**：接口、DTO、枚举、事件、数据库字段、状态值、权限标识等跨模块契约必须先冻结，再允许 A / B 模块并行。
6. **边界外问题先停止**：任何 agent 发现必须改允许范围外文件时，必须停止并回报原因、建议改哪些文件、影响哪个计划项，不能自行扩大范围。
7. **推荐合并顺序**：共享契约 / 基础改动 → 各模块 agent 按依赖顺序合并 → 集成检查 / 回归验证。
8. **只支持有限并行**：互不重叠的模块实现可以并行；同一代码区域、同一共享文件、基于旧实现写测试、依赖未冻结接口写前端等场景禁止并行。

## 最少分级对应文档要求

这里只保留文档组织所需的最少分级映射；任务分级本身、是否进入文档流、是否允许跳过，以 `../cool-project-stack/SKILL.md` 为准。

### L1

- 通常不要求完整模板文档
- 但至少要有简短改动说明或明确任务记录

### L2

- 如果总控已判定进入文档流，开发前至少补：需求说明、技术设计、开发实施
- 有接口变更：补 API 文档
- 有数据库变更：补数据库文档

### L3

- 开发前至少补：需求说明、产品设计、技术设计、开发实施、测试清单、交付说明
- 有接口变更：必须补 API 文档
- 有数据库变更：必须补数据库文档

### L4

- 开发前补全套文档
- 必须写清楚跨端配合方式、依赖关系、联调顺序
- 只要有接口变化，必须补 API 文档
- 只要有数据结构或表结构变化，必须补数据库文档

## 文档输出位置

- 当前任务发生在模板仓库 `base` 目录内，默认输出到 `base/docs`
- 当前任务发生在具体业务项目中，默认输出到项目根目录 `docs`
- 文档目录结构与命名规则优先参考 `../cool-project-stack/references/doc-structure.md`
- 不要把所有内容都堆到一个总文档里，优先采用“系统长期文档 + 模块专项文档”结构

## 多期功能文档组织规范

只要一个功能会拆成两期及以上迭代，默认按“模块目录 + 模块 README + 各版本文档”组织，不要把每一期文档单独散落在 `docs/` 根目录，也不要只留下一个后来谁都看不懂的总文档。

### 1. 默认落点

多期功能文档默认放在：

- `docs/01-modules/模块名/`

不要这样做：

- 在 `docs/` 根目录平铺 `xx-v0.1.md`、`xx-v0.2.md`、`xx-v1.0.md`
- 每一期单独建一个互相没有导航关系的目录
- 只新增版本文档，不维护模块入口 README

### 2. 模块 README 是总入口，必须长期维护

模块目录下必须有 `README.md`，它不是可有可无的说明页，而是这个模块的长期总入口。

`README.md` 至少必须写清楚：

1. **模块背景**：这个模块是干什么的，解决什么问题
2. **版本规划**：现在有哪些版本，后面预计还有哪些阶段
3. **推荐阅读顺序**：第一次接手应该先看什么，再看什么
4. **当前版本入口**：当前正在开发或当前已上线的版本是哪个
5. **长期约束说明或总览入口**：哪些规则是跨版本长期有效的，或者跳到长期说明文档去看

只要模块继续演进，README 就必须同步更新，不能写完第一版后长期不管。

### 3. 哪些文档应该按版本拆

下面这些文档，默认按版本拆：

- 需求文档
- 技术设计文档
- 数据库文档
- 开发实施文档
- 如果版本差异明显，测试文档和交付文档也可以按版本拆

推荐做法是：先看当前项目已有风格。如果项目已有中文编号文档，则按版本子目录继续使用中文编号命名，例如：

- `README.md`
- `长期约束说明.md`
- `核心实体说明.md`
- `v0.1/01-需求说明.md`
- `v0.1/02-产品设计.md`
- `v0.1/03-技术设计.md`
- `v0.1/04-数据库设计.md`
- `v0.1/05-接口说明.md`
- `v0.1/06-开发实施.md`
- `v0.1/07-测试清单.md`
- `v0.1/08-交付说明.md`
- `v0.1/09-任务执行卡.md`

只有在当前项目已经稳定使用英文编号风格时，才继续沿用同一套英文编号命名。

但一个模块内只能选一种版本组织方式，不要一半按平铺命名、一半按子目录命名。

### 4. 哪些文档应该保持模块级长期共用

下面这些内容，不要每个版本都复制一份，默认保持模块级长期共用：

- 模块 README
- 长期约束说明
- 稳定后的核心实体说明
- 模块总览文档

判断规则：

- **只对某一个版本成立**的内容，写进对应版本文档
- **跨多个版本都成立**的内容，写进模块级长期文档

如果一个核心实体、约束规则、模块边界已经稳定，后续版本继续引用它，不要每个版本都重新抄一遍。

### 5. 执行卡不是模块永久总文档

任务执行卡的定位是：

- 任务级文档
- 迭代级文档
- 当前阶段推进记录

它不是“这个模块永久只维护一张总执行卡”。

明确规则：

- 不同版本，要创建各自的执行卡
- 同一版本下，不同开发任务，也可以各自建执行卡
- 执行卡用于记录当前任务怎么推进，不用于替代模块 README 或长期文档

不要把模块的长期背景、所有历史版本、所有后续计划都塞进一张执行卡里。

### 6. README 必须负责串联版本文档

后续版本越来越多时，最容易乱的原因不是文档少，而是**没有统一入口**。

所以模块 README 必须承担串联责任，至少要包含：

- 版本列表
- 每个版本解决的问题
- 每个版本对应文档链接
- 建议先读哪一版，再读哪一版
- 当前版本和历史版本的区别

不允许出现这种情况：

- 版本文档平铺在目录里，但没人知道先看哪个
- 新人只能靠文件名猜顺序
- AI 只能自己扫描目录猜“最新版本”

### 7. 新版本基于旧版本增强时，禁止整份复制重写

如果后续版本是在上一版基础上增强，不要把上一版所有内容整份复制一遍再改几个字。

正确做法：

1. 在新版本文档开头明确写：**本版继承自哪个版本**
2. 明确列出：**本版新增了什么、调整了什么、废弃了什么**
3. 没变化的内容，直接引用上一版或模块级长期文档
4. 只有真正变化的部分，才在新版本里展开重写

推荐写法示例：

- `本版基于 v0.1 增强，未变更的角色定义、核心状态流转、基础数据结构，继续沿用 v0.1。`
- `本版新增 teacher 端审核节点，调整消息通知规则，其余接口约定不变。`

这样做的目的，是避免：

- 文档越来越重复
- 同一规则在不同版本里写出多个说法
- 后续维护时不知道该改哪一份

### 9. AI 执行硬规则

AI 在补多期功能文档时，默认必须遵守：

1. 先找到对应模块目录，没有就先在 `docs/01-modules/模块名/` 下建立模块入口
2. 先更新模块 `README.md`，再新增本期版本文档
3. 先判断哪些内容是版本专属，哪些内容应该放模块长期文档
4. 新版本如果继承旧版本，必须写清继承关系和差异点

6. 写完后检查 README 是否已经把所有版本文档串起来

只要 README 没有把版本关系讲清楚，就不能算“文档组织完成”。

## 开工前最少文档门禁

开始编码前，最少需要满足以下条件：

- L1：有简短改动说明或明确任务记录
- L2：至少有需求说明、技术设计、开发实施
- L3 / L4：至少有需求说明、产品设计、技术设计、开发实施
- 进入开发前文档产出阶段的任务：开发实施文档、任务执行卡或单独协作计划中，必须有《多 Agent 协作计划》或等价章节
- 涉及接口联调，必须再补：接口与数据结构说明
- 涉及数据库变更，必须再补：数据库设计

如果这些文档还没有写出来，不应该直接进入正式编码阶段。

## 必须写清楚的内容

- 本次要做什么
- 为什么这样做
- 文件放哪里
- 关键接口或关键页面是什么
- 数据库怎么设计，字段是什么意思
- 如何联调
- 如何验收
- 多 Agent 怎么分工、交接、确认和处理返工
- 还有哪些风险

## 开发完成后必须补的文档动作

- 更新 `交付与变更说明`
- 更新 `联调与测试清单`
- 更新 `docs/README.md` 中的目录导航、阅读顺序或新增模块入口
- 更新 `系统功能说明文档` 中本次新增或变更功能
- 如果本次改动影响系统模块边界、角色权限、部署配置、外部依赖或页面入口，继续更新 `系统说明文档`

## 完成标准

- 看文档的人不需要猜目录和落点
- 初级开发者可以按文档继续开发
- 文档和当前项目结构一致，不是空泛模板
- 文档顺序能支撑“先设计、再开发、再联调、再交付、再回写系统文档”
